# Existing Hostinger site: v2.1 update

Your existing database and Firebase administrator are reused. Do not create another database or Admin for this update. No ZIP or server build is required.

1. Stop invoice entry during the update. Export the current database from phpMyAdmin, and download a copy of the hosted files, especially `.env` and `storage/`. Keep the original `APP_KEY` with the backup.
2. Open hPanel → Websites → your website Dashboard → Databases → Management → phpMyAdmin. Select the **existing** database that the hosted `.env` uses.
3. Since you already imported `migrate-v2.0.sql`, import **only `database/migrate-v2.1.sql`**. Do not re-import `schema.sql`, `seed.sql`, or `migrate-v2.0.sql`. The v2.1 patch adds receipt snapshots and the Other payment method; it can be repeated safely and does not reset invoice totals, shipping settings or users.
4. The **`gstsoftware` project root itself is the single deployment folder**. It contains `public`, `src`, `config`, `templates`, `database`, `bin`, `docs`, `vendor`, `storage`, `.htaccess` and the complete `.env`. In Hostinger File Manager, open the server `public_html` and upload/replace the application contents from this root in one operation while preserving the nested structure. There is no local `public_html` deployment copy and the result must not contain an extra nested project folder.
5. **Do not delete, shorten, regenerate or partially replace `.env`.** This project root retains every existing environment variable, including database, Firebase, Admin, mail, backup and integration settings. It also retains the existing `storage` tree. File Manager should merge folders and replace same-named application files; it should not erase server-only stored uploads.
6. No `.env` change is needed if the site already works. Keep the current database host/name/username/password, `APP_KEY`, Firebase values and `BOOTSTRAP_ADMIN_EMAIL`. `APP_URL` should remain your actual `https://YOUR-DOMAIN/public` URL. Do not replace full Hostinger database names with unprefixed examples.
7. In hPanel, purge/clear the website cache if Hostinger cache is enabled. If the domain uses Cloudflare or another CDN, purge that cache too. Then open the site and hard refresh with **Ctrl+F5**. Sign in using the same existing Admin email and Firebase password.
   After the updated assets load, the sidebar/top bar visibly shows **v2.1.2**. If it does not appear, the server is still serving old files or the folders were uploaded into `public_html/public_html` by mistake. If a mixed/partial upload occurs, the page now shows an explicit "Update files are incomplete" message instead of remaining on the loading screen.
8. Go to **Settings → Tax & billing preferences → GST rate on shipping (%)**. Enter your applicable shipping rate and save. The prior default is **0%**; deployment intentionally does not impose a tax rate. New invoice forms use this default; the Shipping GST (%) field can be adjusted before saving. Existing invoices retain their saved rate.
9. Check an invoice with shipping entered **before tax**. Calculation example only: shipping `100` at a selected `18%` adds tax `18`, so shipping contributes `118` to the total. Same-state invoices split that tax into `9` CGST + `9` SGST; different-state invoices use `18` IGST. “Of which shipping GST” is informational and already included in Total GST.
10. Save/reopen the invoice, download PDF, and check Reports → HSN and GST totals. Check one partial-payment invoice, clear its balance, and download the receipt. Confirm old invoices, business logo/signature and bank details still open correctly. Resume billing after these checks.

If the site still uses a v1.1 schema, first take the backup and import `migrate-v2.0.sql` **once**, then import `migrate-v2.1.sql`. For a completely new empty installation, `schema.sql` plus `seed.sql` already include the latest schema; no migration files are then needed.

Firebase Admin password changes and permanent Firebase user deletion need the project's service-account configuration in addition to the normal Firebase web configuration. Normal existing login does not require recreating the Admin or resetting its password. Verify those actions on a disposable Owner/Staff account after deployment. Never delete the working Admin for testing.

Credit receipts created after this update preserve business/customer details. Older receipts are frozen using the details available at migration time; the application cannot reconstruct details already overwritten before the upgrade. Once an account has clearance receipts, its credit invoices cannot be edited/cancelled, to prevent rewriting settled history. Further credit invoices and clearances are supported. Credit-note refunds are separate from credit-clearance payments.

Hostinger's official [database import/configuration guide](https://www.hostinger.com/support/1864324-how-to-upload-and-set-up-your-database-at-hostinger/) describes the hPanel/phpMyAdmin import flow. The steps above are specifically for this application's **existing** database, not a fresh database setup.
